## What is Testing?
- "Testing is the process of demonstrating that errors are not present."
- "The purpose of testing is to show that a program performs its intended functions correctly."
- "Testing is the process of finding errors in a program (not in software code)."
### Testing Principles
- Exhaustive testing is impossible
	- i.e. cant test every possible input on a function
- Defects cluster together
	- Errors arise around other errors, easier to find
- Beware of the pesticide paradox
	- Over time, changes are made to the program, cannot run same tests forever
- Testing shows the presence of defects, not their absence
	- Testing cannot prove that a program is bug-free
- Absence-of-errors is a fallacy
	- e.g. Program can be error-free but usability is terrible
- Early testing saves time and money
- Testing is context dependent
	- Testing for an e-commerce site would be different to that of a space ship

# People Based Testing
- Walkthrough
- Inspection

These are all reviews - different types of group meetings yet with the sae purpose, i.e. to identify problems, but not to solve them.
- + Acceptance testing
## Walkthrough
- Can be a large group of people
- Only the presenter prepares
- If the element is code, then the presenter steps through the code line by line with a set of test inputs
- Often used to communicate information about the element under test as well as to discover defects
## Inspection
- Visual inspection of the element by a team of 4-7 people
- Uses a checklist approach to inspect a limited set of aspects of the element
- Everyone in the team must participate actively
- Everyone in the team must prepare!
## Technical Review
- This is very similar to inspection, but is more informal
- The review group is usually slightly smaller
- There isn't any checklist to follow - the meeting flows more naturally
### Team
- 1 Moderator
- 1 Recorder
- 2 or more Reviewers
### Responsibilities
- Everyone involved is responsible for the quality of the review and its report
- The review is complete when an agreed written report on the product's status is made available to everybody involved
	- ID, date, start/end time, unit ID, description, materials used, participants, issues list, appraisal of unit (accepted / not accepted)
#### Moderator
- Schedule the inspection, book the venue, collect & distribute information prior to the review meeting
- Conduct the meeting:
	- Introduct each person, check everyone has the materials, then begin...
	- Keep people to the agenda, be the "time manager", ... get the final consensus
### Recorder
- Gather information and produce an accurate report of the inspection
	- Use flip charts / whiteboard / OHP / word processor with projector
	- Record issues and keep detailed notes
	- Use neutral language, be accurate and unambiguous
- Might not take an active role in the inspection process
#### Reviewers
Typical roles taken are:
- a domain expert
- a tester
- a developer
## Acceptance Testing
### What is an Acceptance Test?
- This is a test run by the customer on their site to confirm (or otherwise) that software is acceptable
- Often is is written by the provider of the software but it must be agreed with the customer
- It forms part of the negotiated contract between the supplier and customer
### Why do acceptance testing?
- To transfer the software to the customer
- To get the customer to sign-off software as being complete / acceptable (to get paid)
- To finish a project's production phase
- To agree with the customer what remains to do before the software is acceptable
### Who is involved?
1. Customer or their representatives
2. Software developer or test engineer
3. Project manager
4. Any contractual officers
### How to identify and write acceptance tests
#### Use Cases
- They cover the complete functionality of the system
- They are readily understood by the customer
- They are in the form of a dialogue between the user and the system

This gives all the test cases + other info:
1. An ID for the test plan
2. An introduction (e.g. strategy taken)
3. A summary of requirements
4. A copy of your documentation
5. A summary of the procedure to follow
6. Which features are being tested, which are *not* being tested, any justification
7. A schedule for the testing
8. A note of any pass or fail criteria for the whole event
9. List each acceptance test!

This gives instructions for each test, including
1. an ID, description & note of constraints
2. Which use case/s is/are covered
3. The resources required
4. The step-by-step procedure to follow
### Handling Faults Found
- *Known faults* should be documented and presented to the customer prior to the start of the acceptance test
- *Further faults* found must be documented together with an agreed action:
	- serious fault: the software is unacceptable
	- minor fault: use the software but fix the fault by an agreed time
	- negligible fault: the software is OK but document the incident
### After Testing...
1. View all the failed tests and determine what caused the test to fail
2. After a defect has been repaired, re-test the application to verify that changes have occurred and that the fix did not introduce additional problems or unexpected side-effects
